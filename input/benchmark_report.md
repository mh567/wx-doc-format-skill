# LLM 增强基准对比测试报告

## 摘要

本测试评估 wx-doc-format 在纯规则基准和全量 LLM 增强两种模式下的格式规范性、语义修正收益与运行效率特征。测试覆盖 6 个 DOCX 文档，其中接口类和方案类各 3 个，共得到 12 条有效结果。测试环境为 wx-doc-format 0.8.5、Python 3.14、DeepSeek API。核心结论：abc 模式没有引入非模板样式，列表重启问题也保持为 0，但在部分文档中新增了标题层级警告，风险提示总数从 15 增至 18。LLM 增强在方案类文档上收益更明显，主要体现为功能点列表识别、章节层级修正、表格语义和题注修正。

## 测试设置

测试文档包括 3 个接口类文档和 3 个方案类文档，覆盖不同规模和类型的真实企业技术文档。

测试模式包括 off 和 abc。off 表示纯规则基准，仅执行解析、规范化、模板渲染和审计。abc 表示全量 LLM 增强，强制执行 Phase A、Phase B、Phase C，分别覆盖段落角色、章节结构、表格和题注语义。

## LLM 增强效果分析

| 文档 | 类别 | Phase A | Phase B | Phase C | 总修正 | LLM 错误 |
|---|---|---|---|---|---|---|
| 接口文档 A | 接口类 | 3 | 0 | 0 | 3 | 2 |
| 接口文档 B | 接口类 | 2 | 4 | 0 | 4 | 1 |
| 接口文档 C | 接口类 | 6 | 7 | 0 | 7 | 1 |
| 方案文档 A | 方案类 | 15 | 19 | 0 | 19 | 1 |
| 方案文档 B | 方案类 | 0 | 2 | 11 | 11 | 0 |
| 方案文档 C | 方案类 | 3 | 0 | 3 | 3 | 1 |

典型修正类型包括：连续功能点识别为列表、封面标题降级、API 示例标签降级、API 参数表识别、数据表表头识别、顶层章节层级修正、附录表格前小节标题识别、题注文本生成。

接口类文档的单文档平均修正数为 4.67，方案类文档为 11.00。方案类文档的 LLM 修正数量明显更高，说明全量增强更适合章节复杂、功能点密集、表格题注混杂的技术方案类文档。

## 效率分析

off 模式路径开销极低，纯规则转换在数秒内完成。abc 模式下各文档之间存在分钟级间隔，说明 LLM 路径受到远端调用、超时和重试顺序影响。

在 12 次 abc 转换中共记录 6 条 LLM 错误，主要集中在 Phase B 和 Phase C 的 30 秒超时。部分文档的 Phase C 出现 Patch 校验失败。

优化建议：补充 wall_time_sec 和 output_size_kb 精确测量；Phase B 按章节分片调用以控制 prompt 体积；Phase C 按表格批次调用并增加 JSON schema 预校验；记录每个 Phase 的耗时、token 估算和应用率。

## 结论与建议

LLM 增强的边际收益主要体现在语义结构层面：识别连续功能点、纠正封面元信息、调整章节层级、改善表格与题注语义。本轮数据中 abc 模式应用了 47 项最终修正，方案类文档收益更明显。

从规范性角度，abc 模式保持了模板样式合规，未引入非模板样式，也未引入列表重启问题。但部分样本新增了标题层级警告，说明章节结构调整仍需审计兜底和人工复核。对正式交付文档，建议将 abc 模式作为语义增强和结构修正工具，输出后继续以样式合规性和结构审计指标作为硬性复核标准。

当前限制集中在效率和稳定性：Phase B/C 存在超时，Phase C 偶有校验失败。后续改进应优先减少 prompt 体积、分片处理大文档、记录精确耗时。综合本轮结果，LLM 增强适用于结构混乱或语义歧义较多的文档；对规则路径已稳定、审计指标接近零的短文档，纯规则 off 模式仍是更高效的基准选择。
