# LLM 增强基准对比测试报告

## 摘要

本测试评估 wx-doc-format 在纯规则基准和全量 LLM 增强两种模式下的格式规范性、语义修正收益与运行效率特征。测试覆盖 6 个 DOCX 文档，其中接口类和方案类各 3 个，共得到 12 条有效结果。测试环境为 wx-doc-format 0.8.5、Python 3.14、DeepSeek API、模板 assets/技术文件格式及书写要求.docx。核心结论是：abc 模式没有引入非模板样式，列表重启问题也保持为 0，但在 3 个文档中新增了标题层级警告，风险提示总数从 15 增至 18。LLM 增强在方案类文档上收益更明显，主要体现为功能点列表识别、章节层级修正、表格语义和题注修正。

## 测试设置

测试文档包括 3 个接口类文档：接口控制文件2、接口文档0708、身份接口策略下发部分；3 个方案类文档：IAM全球部署高可用、生物特征认证系统集成方案、身份对象模型。

测试模式包括 off 和 abc。off 表示纯规则基准，仅执行解析、规范化、模板渲染和审计。abc 表示全量 LLM 增强，强制执行 Phase A、Phase B、Phase C，分别覆盖段落角色、章节结构、表格和题注语义。

## 效率分析

benchmark_results.json 未保存 wall_time_sec，因此无法给出严格的端到端耗时对比。根据 wx_output/benchmark 目录中文档与报告文件的修改时间，off 结果集中生成在 2026-07-11 09:52:44 至 09:52:52，纯规则路径开销很低。abc 结果分布在 2026-07-11 09:22:29 至 09:58:47，各文档之间存在分钟级间隔，说明 LLM 路径受到远端调用、超时和重试顺序影响。该推断只适合作为运行特征参考，后续应在基准脚本中直接记录 time.perf_counter 的 wall_time_sec。

详细报告记录了 6 条 LLM 错误。接口控制文件2 的 Phase B 和 Phase C 均发生 30 秒超时。接口文档0708、身份接口策略下发部分的 Phase C 发生 30 秒超时。身份对象模型的 Phase B 发生 30 秒超时。IAM全球部署高可用的 Phase C 出现 Patch validation failed，包含 3 个校验错误。

优化建议包括：补充 wall_time_sec、input_size_kb、output_size_kb；Phase B 按章节分片调用；Phase C 按表格批次调用；对 Phase C 增加更严格的 JSON schema 预校验；记录每个 Phase 的耗时、token 估算、超时次数和应用率。

## 结论与建议

LLM 增强的边际收益主要体现在语义结构层面：它能识别连续功能点、纠正封面元信息、调整章节层级，并改善表格与题注语义。本轮数据中，abc 模式应用了 47 项最终修正，方案类文档收益更明显。

从规范性角度，abc 模式保持了模板样式合规，未引入 unexpected_styles，也未引入列表重启问题；但它在 3 个样本中新增标题层级警告，说明章节结构调整仍需审计兜底和人工复核。对正式交付文档，建议将 abc 模式作为语义增强和结构修正工具，输出后继续以 unexpected_styles、heading_hierarchy_warnings、risk_warnings_count 作为硬性复核指标。

当前限制集中在效率和稳定性：Phase B/C 存在 30 秒超时，Phase C 还出现过 patch 校验失败。后续改进应优先减少 prompt 体积、分片处理大文档、记录精确耗时，并将 Phase C 的操作空间进一步收窄。综合本轮结果，LLM 增强适用于结构混乱或语义歧义较多的文档；对规则路径已稳定、审计指标接近零的短文档，纯规则 off 模式仍是更高效的基准选择。
