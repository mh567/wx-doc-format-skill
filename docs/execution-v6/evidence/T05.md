## FIX 轮：端到端发现的顺序回归

首轮实现后，6 项测试通过，但端到端验证发现一个测试未覆盖的顺序回归。样例 DOCX（源顺序即下列顺序）：

```
p 第一项              [direct numPr, numId 1, ilvl 0]
p 第二项              [direct numPr, numId 1, ilvl 0]
p 第二项后的续接正文。
p 表格前的说明。
tbl (2x2)
p 尾部正文。
```

修复前，第 2 个列表项拥有四个尾部块的 `content_blocks` 为 `[第二项, 续接正文, 表格前的说明, 尾部正文, table]`（所有正文段在前、非正文块在后），其 AST `children` 为 `[第二项, table, 尾部正文, 续接正文, 表格前的说明]`（按节点 id 字符串排序后追加），渲染正文顺序为 `第二项, tbl, 尾部正文, 续接正文, 表格前的说明, 表 1`。三处缺陷：归属记录不是源序、AST children 与归属记录互不一致且都不是源序、生成题注落在表格之后（违反 AGENTS.md 决策 3）。

### 实际机制（确认与证伪）

确认的根因（首轮实现层面）：

1. `source_ast.materialize_list_semantics` 以 `expand_owned([自身, *owned_content(续接段), *owned_blocks(非正文块)])` 组装归属记录，把所有续接段拼在所有非正文块之前。`lists.py` 同样把 `continuations` 与 `child_blocks` 收集为两个独立列表。两者都已丢失源序。
2. 于是四个尾部块的内容移动候选不带任何排序键。`transaction._order_stage_decisions` 对同类移动按 `(new_parent_id, index, target_node_id)` 排序、无 index 时按节点 id 字符串排序，`_apply_move_node` 无 index 时追加。children 顺序因此由节点 id 决定，与源序无关。
3. 生成题注候选由 `captions._generated_caption_candidates` 在基础 revision 上按「目标表的父节点与槽位」计算 `parent_id` / `index`。表在同一批次里被移动到列表项下，而事务先落地全部 `create_node`、再落地 `move_node`，因此题注留在文档根、排在列表之后。

证伪的猜测：题目提示「`expand_owned` 的拼接也解释了题注落在表格之后」。该拼接只影响归属记录与内容移动顺序，改变它并不能把题注移到表格之上。题注落在表格后的直接机制是「题注在基础 revision 上锚定、表在同一批次移走、创建先于移动」，与归属记录的拼接无关。因此题注需要在锚定层面单独修复。

### 修复（落在归属方）

1. `lists.py`：`analyze_lists` 新增源序归属记录 `owned_content`（每项 `node_id / owner_item_id / list_id / scope_id / state`）。续接段与子块在 `_emit_group` 与隐式尾部扫描中按扫描顺序（即源序）追加；`continuations` / `child_blocks` 保留为同一记录的过滤视图。
2. `source_ast.py`：`materialize_list_semantics` 的 DOCX 派生列表项直接消费 `owned_content` 组装 `content_blocks`，正文段与非正文块交错保持源序；内容移动候选携带 `source_index`（该块在项源序归属记录中的位置，含物化图片展开）。
3. `transaction.py`：同类移动在 `index` 之后按 `source_index` 排序，`move_node` 保持既有宽松 `applied` 谓词（无 index 即只校验节点在目标父节点下），因此锚定创建的插入不会让移动的幂等判定失真。`_order_stage_decisions` 把携带 `anchor_node_id` 的创建分流到移动之后；`_apply_create_node` / `_applied_create_node` 在锚点当前父节点下按 `anchor_position` 解析父节点与槽位。
4. `captions.py`：生成的题注候选携带 `anchor_node_id = 目标` 与 `anchor_position`（表在前、图在后），落位改由事务相对锚点当前位置解析，因此表在同批次被移动到列表项下时题注仍紧贴其上方。

## 工作项落地

1. **列表项可承载异构内容**（工作项 1）。`source_ast.materialize_list_semantics` 的 `content_blocks` 对隐式与显式列表项统一填写：`paragraph`（自身或续接）、`table`、`image`、`quote`、`code` 都通过 `_implicit_tail_content` 的裁决进入归属记录，`child_lists` 单独承载子列表容器。判定依据是块的 `kind` 与 `block_type`，不依赖列表项是否有源子节点。
   复审更正两处口径：`formula` 在本链路上是段落角色而非独立单元/容器类型，公式段落经 `paragraph` 通道以 `ITEM_CONTINUATION` 进入归属记录，不会记为 `ITEM_CHILD_BLOCK`；`note` 属于受保护角色，`_implicit_tail_content` 在受保护块处停止扫描，因此注记当前**不**归入列表项，见残留 14。
2. **子列表后的续接正文归属父项**（工作项 2）。`_tail_content_owner` 在列表段之后继续扫描：正文段归前一个列表项并记为 `ITEM_CONTINUATION`；子列表之后的正文段归回承载该子列表的父项，不归子列表的最后一项。`test_t05_continuation_after_child_list_belongs_to_parent_item` 覆盖。
3. **`list_item_map` 接缝不变**（工作项 3）。`item_map` 仍为「源列表项 id 到所属列表容器 id」，未改名或改形；附录模块的消费方式未变。`test_t05_list_item_map_seam_keeps_its_shape_and_consumers` 与全量附录审计共同守住。
4. **隐式运行尾部归属与约束 5**。尾部内容扫描在新列表段、受保护块或运行结束时停止，因此正文段不会独立终止外层列表（README 约束 5），同时 `[列表项][正文][列表项]` 仍保持两个隐式组（T04 行为不回退），由 `test_t05_body_between_items_keeps_two_implicit_groups` 覆盖。
5. **源序是一般不变量**（FIX 轮）。归属记录、AST children 与渲染顺序都用同一份源序：`owned_content` 给出源序，`source_index` 让事务按源序追加移动，端到端测试覆盖交错尾部与以表格开头的尾部两种尾部形态，不针对具体样例特判。
