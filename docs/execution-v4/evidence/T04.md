## 独立审查修复轮 1

### 问题闭环

1. 原生增强响应只有 `completed` 状态可以继续进入 Resolver 和事务。陈旧视图、非法 Patch、陈旧目标、超时、调用失败、能力缺失及其他非成功状态均在渲染和发布前返回失败。检查点中的响应保留未应用状态，输出文件不会产生。
2. 恢复入口先重新解析当前 SourceFacts，再核对源内容、parser、外部资源、真实请求文件、模板、当前有效配置、合同和模块身份。全部核对发生在响应记录前。
3. 未显式传入的 CLI 值从检查点恢复。显式传入的 input、output、template、profile、policy 和关键选项保留为当前有效配置，配置摘要不一致时稳定拒绝。
4. 等待检查点恢复保存的 Source AST、有效决策账本、内容覆盖、呈现覆盖、事务摘要和恢复阶段。已有有效账本修订得到保留。
5. 完成检查点保存完整 Normalized 1.0 对象。合同 schema 与运行时校验同时接受完整对象、`None` 和已有 Source AST 兼容形态。
6. 渲染器使用底层 OOXML 单元格元素作为生命周期身份，消除了 Python 数值对象身份复用引发的空段落和 `table_body` 样式落点差异。
7. 完成状态的幂等重放继续校验真实 requests 文件和 response 内容。原请求 AST 与最终提交 AST 不再执行无效同一性比较，内容变化仍稳定冲突，输出字节保持不变。

### 等价性定义

多阶段文件恢复和同响应在线执行必须同时满足完整 Normalized 1.0、最终 Source AST、语义摘要、呈现摘要、`saved_output_audit` 结果一致。输出结构还比较表格数量、每个单元格的段落数量、空段落数量、段落样式序列、编号属性数量和题注 `SEQ` 域指令。

最终 DOCX 比较按 OPC 成员名排序，对每个解压后的成员名和成员字节计算统一 SHA 256。该比较排除 ZIP 条目顺序、压缩参数和 ZIP 时间戳；当前未排除 relationship ID 或 XML 顺序，约束强于仅比较可见文本。

## 独立审查修复轮 3

### 响应应用状态

Checkpoint 2.0 运行时校验会识别 native v2 文件检查点，并将每个 response 的应用元数据与检查点状态及事务集合交叉验证。

1. `waiting_external` 中的响应必须保持 `applied=false`，`apply_started` 不能为真，且不能携带 transaction 应用绑定。
2. `completed` 与 `completed_with_warnings` 中的响应必须为已应用状态，`apply_started=false`，其 transaction ID 与内容摘要必须精确存在于 `applied_transactions` 和 `transaction_content_digests`。
3. 不一致返回稳定的 `response_application_state_mismatch`。校验发生在 completed 快捷返回和 response map 构造前，篡改后的检查点与已有输出均不会被写入。

对应失败测试覆盖等待与完成状态下四类应用元数据，共 `8 failed, 35 deselected`。修复后为 `8 passed, 40 deselected`。

### 实时候选基线

新增确定性内建候选构建函数，以当前 SourceFacts、Source AST 和源路径重建 scope、structure、protected content、list、appendix、table 与 caption 候选。`prepare_native_resume` 在读取和记录外部 response 前计算 live candidate baseline，并与检查点值比较。该检查独立于 baseline 与 `run_id` 的自洽关系。
