# native-v2 架构收敛方案

日期：2026-09-12

## 目标

在现有 C3 native-v2 实现上完成架构收敛，确保普通转换、LLM 复核、文件恢复和发布验收遵循同一条可追踪主链。范围只覆盖架构一致性、合同强度、代码职责和最终验收，不新增业务能力。

目标主链固定为：

`SourceFacts → 语义 Module → CandidateSet → Resolver → Transaction → Source AST → Normalization → Render → Audit → Review → Publish`

## 防止复审新增问题的固化机制

每张工单必须依次完成以下闭环：

1. 固定基线提交和允许修改范围。
2. 先增加能证明缺陷的红灯测试。
3. 实现改动并运行工单内定向测试。
4. 由独立审查检查 Standards、Spec、接口和回归影响。
5. 修复审查意见并重新运行定向测试。
6. 运行与真实 Markdown、真实 DOCX 或编译运行时相关的证据命令。
7. 形成证据文件，记录提交、命令、退出码、测试结果和未关闭事项。

最终复审只针对一个固定候选提交。复审发现的问题必须满足以下三种状态之一：已修复并有回归测试，明确属于外部验收门禁，或新建后续工单并阻止当前工单关闭。不得用“测试通过”替代架构结论。

## 四张可执行工单

### AC-1 统一复核候选重处理链

目标：消除 `native-reviewer` 内部重复调用 Resolver、Transaction、Normalization、Render 和 Audit 造成的隐藏子流水线。

完成后，复核 Module 只负责复核请求、范围校验、候选接受和回滚。候选重处理通过与普通转换相同的已注册 Module 或子执行计划完成。

必须提供：接受候选、拒绝候选保留基线、候选事务冲突、候选保存后审计失败四类回归证据。

### AC-2 固化能力合同和执行调度

目标：降低 `dict[str, Any]`、字符串能力名和隐式注册顺序带来的漂移风险。

完成后，关键能力具有版本化合同，Module 依赖关系可以显式验证，执行计划生成具备确定性。`request.options` 和 `services` 只能承载明确声明的运行时服务，不能成为未声明的业务数据通道。

必须提供：能力版本不匹配、缺失依赖、循环依赖、同阶段顺序变化、未声明读写和非法载荷六类负向证据。

### AC-3 收敛代码职责和入口边界

目标：降低大文件集中度，减少开发诊断入口与公开入口之间的隐式耦合。

完成后，语义识别、事务、规范化渲染、复核、检查点和发布职责各有清晰归属。稳定 CLI 参数保持兼容，legacy 诊断能力只在开发路径可用，发布运行时继续拒绝 legacy 生产表面。

必须提供：稳定入口回归、发布包 legacy 拒绝、源码与编译模块清单一致、无退役模块导入和拆分后全量回归证据。

### AC-4 综合验收、独立复审和发布准备

目标：在一个固定候选提交上完成架构、规格、真实文件和编译运行时的综合确认。

必须完成：

1. 全量测试和差异检查。
2. 真实 Markdown、真实 DOCX、文件协议、恢复、复核和保存后 OOXML 审计。
3. macOS ARM64 与 Linux ARM64 编译运行时 smoke。
4. 独立复审及修复后的二次复审。
5. Kylin V10 ARM64 真机验收。
6. Word/WPS 页面视觉、分页和域更新确认。
7. 远程推送、标签、Release 和远程安装验证。

## 收敛判定

AC-1 至 AC-3 完成，表示架构基本收敛。AC-4 的本地与独立复审完成，表示候选具备交付条件。Kylin 真机、Word/WPS 和远程发布仍属于独立外部门禁，全部通过后才可宣布正式发布完成。

## 明确不纳入本轮

1. 不新增模板能力、LLM 能力或输入格式。
2. 不改变稳定 CLI 参数名称和既有公开报告合同，除非先增加兼容测试。
3. 不移动或删除 `_build/`、`paseo.json` 及无关用户改动。
4. 不在架构工单中执行远程 push、tag 或 Release，除非获得单独授权。
